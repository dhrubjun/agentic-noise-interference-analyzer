# V0.3 Engineering Specification

Agentic Noise & Interference Analyzer

Version: V0.3  
Name: Event & Anomaly Detection  
Status: Proposed baseline  
Depends on: V0.2 Noise & Interference Characterization

# 1. Objective

V0.3 extends the validated single-channel DSP analyzer from static signal characterization toward detection of time-localized changes.

The objective is:

> Given one validated sampled signal, detect time intervals whose measured signal properties deviate significantly from an estimated baseline, and describe those intervals using reproducible numerical evidence.

V0.3 remains a deterministic DSP system.

It does not use:

- LLMs
- Ollama
- machine learning
- neural networks
- Isolation Forest
- agentic reasoning
- automatic source identification
- causal inference

The processing philosophy becomes:

```text
Signal
  ↓
Validated V0.1/V0.2 DSP
  ↓
Short-time measurements
  ↓
Baseline estimation
  ↓
Deviation measurement
  ↓
Event segmentation
  ↓
Structured event evidence
```

The analyzer detects measurable deviations.

It does not diagnose their physical cause.

---

# 2. Meaning of "Event" and "Anomaly"

These terms must have precise meanings.

## 2.1 Event

An event is:

> A contiguous time interval where a selected measured feature satisfies a defined event-detection rule.

Examples:

```text
short-time RMS increased
band power increased
spectral centroid changed
short-time peak amplitude increased
```

An event is therefore a measurement result.

## 2.2 Anomaly

For V0.3, anomaly means:

> A statistically significant deviation of a measured feature from its estimated baseline.

This does not mean:

```text
system failure
fault
dangerous condition
unknown interference source
```

Those are interpretations requiring additional evidence.

For example, V0.3 may report:

```text
Short-time RMS between 4.25 s and 4.81 s
was 8.2 robust-scale units above the baseline.
```

It must not report:

```text
A machine fault occurred at 4.25 s.
```

---

# 3. Supported Input

V0.3 retains the current assumptions:

- single-channel input
- real-valued samples
- uniformly sampled data
- known sampling frequency
- offline processing
- validated finite samples

V0.3 operates on the original signal and validated V0.1/V0.2 measurements where appropriate.

Multichannel anomaly detection belongs to V0.4 and later versions.

---

# 4. Core Architectural Rule

V0.3 shall separate four operations:

```text
Feature measurement
        ↓
Baseline estimation
        ↓
Deviation scoring
        ↓
Event segmentation
```

These operations must not be collapsed into one opaque "anomaly detector."

This allows each stage to be independently validated.

Example:

```text
Signal
  ↓
Short-time RMS
  ↓
Median baseline
  ↓
MAD-based deviation score
  ↓
Threshold + hysteresis
  ↓
Event intervals
```

The final event must retain the evidence produced by every stage.

---

# 5. Short-Time Feature Measurement

Event detection requires measurements that vary with time.

V0.3 will divide the signal into overlapping frames.

Parameters shall include:

```text
frame_length_samples
frame_length_seconds
hop_length_samples
hop_length_seconds
```

Feature timestamps must have a documented convention.

Preferred convention:

```text
frame centre time
```

The frame length and overlap must always be retained in the analysis metadata.

No hidden window length is acceptable.

---

# 6. Initial Time-Varying Features

V0.3 should begin with a small set of well-understood measurements.

## 6.1 Short-Time RMS

For frame k:

```text
RMS[k] = sqrt(mean(x²))
```

Purpose:

- detect increases in signal energy
- detect bursts
- detect sustained amplitude changes
- detect intermittent disturbances

This should be the first V0.3 event feature implemented.

---

## 6.2 Short-Time Peak Amplitude

For each frame:

```text
peak[k] = max(abs(x))
```

Purpose:

- impulsive disturbances
- large transient excursions

Peak amplitude must remain distinct from RMS because an impulse and a sustained disturbance may have similar peaks but different energy.

---

## 6.3 Short-Time Band Power

V0.2 already provides validated band-power measurement.

V0.3 should extend this into time-localized band power.

Example:

```text
0–250 Hz power versus time
250–1000 Hz power versus time
```

Purpose:

Detect events confined to particular frequency regions.

This is important because an event may occur without a large change in total RMS.

---

# 7. Future-Compatible Feature Interface

The event detector should not depend directly on RMS.

Instead, it should operate on a generic scalar feature series:

```text
feature_times
feature_values
feature_name
feature_units
```

This means future validated measurements could include:

```text
spectral centroid versus time
spectral flatness versus time
line-to-floor ratio versus time
specific harmonic energy versus time
```

without rewriting the event segmentation system.

Only validated features may enter the detector.

---

# 8. Baseline Estimation

An anomaly requires a reference.

V0.3 therefore needs an explicit baseline.

Initial supported methods should be:

## 8.1 Full-Record Robust Baseline

Estimate baseline from the complete feature track.

Initial location estimator:

```text
median
```

Initial scale estimator:

```text
MAD
```

where:

```text
MAD = median(|x - median(x)|)
```

A Gaussian-equivalent robust scale may be calculated as:

```text
robust_scale = 1.4826 × MAD
```

This method is suitable when anomalous periods occupy a relatively small fraction of the recording.

---

## 8.2 User-Defined Reference Interval

Allow the user or later agent to specify:

```text
baseline_start_time
baseline_end_time
```

Only measurements inside this interval are used to construct the baseline.

Example:

```text
0–5 s known quiet period
```

This is important for laboratory measurements where a known baseline period exists.

The analyzer must record which baseline samples were used.

---

# 9. Baseline Limitations

The full-record baseline is not universally valid.

For example:

```text
recording:
50% normal
50% elevated disturbance
```

A single global median may not represent either state correctly.

Therefore V0.3 must not claim that the global baseline is universally correct.

Adaptive baseline tracking is intentionally deferred until there is a validated engineering need.

---

# 10. Robust Deviation Score

For feature value x[k]:

```text
score[k] =
(x[k] - baseline_location)
/
baseline_scale
```

For MAD-based scaling:

```text
score[k] =
(x[k] - median)
/
(1.4826 × MAD)
```

This is a robust standardized deviation score.

For energy-like measurements, initial detection should support one-sided positive deviations:

```text
large positive score
→ feature increased significantly
```

Future detectors may support:

```text
negative deviations
two-sided deviations
```

when scientifically justified.

The score is not a probability.

A score of 6 must not be interpreted as:

```text
99.999% probability of anomaly
```

unless such a statistical model has been separately established.

---

# 11. Degenerate Baseline Handling

A special case occurs when:

```text
MAD = 0
```

This can occur for:

- constant signals
- quantized measurements
- nearly deterministic feature tracks

The implementation must not silently divide by a tiny arbitrary number.

Instead, it shall explicitly report a baseline-scale status such as:

```text
valid
degenerate
insufficient_data
```

Standardized anomaly scores shall only be produced when the baseline scale is mathematically meaningful.

This behaviour must be tested.

---

# 12. Threshold-Based Event Detection

Once a validated deviation score exists, candidate anomalous frames may be identified using a configured threshold.

Conceptually:

```text
score >= start_threshold
→ event candidate
```

Threshold values must be explicit parameters.

V0.3 shall not claim that one universal anomaly threshold works for all sensors and applications.

Reference thresholds may be chosen for synthetic validation.

They are validation settings, not universal physical constants.

---

# 13. Hysteresis

Using one threshold for starting and ending an event can produce unstable event boundaries.

V0.3 should therefore support:

```text
start_threshold
end_threshold
```

where normally:

```text
start_threshold > end_threshold
```

Example:

```text
start event when score >= 6
continue event while score >= 3
```

This prevents a single event from repeatedly switching on and off near the threshold.

---

# 14. Minimum Event Duration

A configurable parameter shall define the shortest accepted event.

Example:

```text
minimum_event_duration = 50 ms
```

Events shorter than this value may be rejected.

This parameter must be stored in the results.

A short event is not automatically noise.

The filtering rule is purely configurable.

---

# 15. Event Gap Merging

Two detected intervals separated by a sufficiently small gap may represent one physical disturbance.

V0.3 should therefore support:

```text
merge_gap_seconds
```

Example:

```text
event
40 ms quiet
event
```

If:

```text
merge_gap = 100 ms
```

the two intervals may be merged.

Again, the merging rule is a configured segmentation rule, not physical interpretation.

---

# 16. Event Timing

Each event shall report:

```text
start_time_s
end_time_s
duration_s
peak_time_s
```

Event timing resolution is limited by the selected:

```text
frame length
hop length
```

The analyzer must not report false precision beyond the available temporal resolution.

---

# 17. Event Measurements

Each detected event should retain numerical evidence such as:

```text
event_id
feature_name
feature_units

start_time_s
end_time_s
duration_s

peak_time_s
peak_feature_value
peak_deviation_score

baseline_location
baseline_scale
baseline_method

mean_feature_value_during_event
maximum_feature_value_during_event

relative_change_from_baseline
```

Where appropriate, event signal statistics may also include:

```text
event_rms
event_peak_amplitude
event_energy
```

These measurements describe the event.

They do not identify its source.

---

# 18. Event-Level Spectral Characterization

Once an event interval has been detected, existing validated V0.1/V0.2 tools may analyze the corresponding signal segment.

Possible measurements:

```text
event PSD
event spectral centroid
event spectral spread
event spectral flatness
event dominant lines
event harmonic families
event band powers
```

This allows comparisons such as:

```text
baseline:
low broadband energy

event:
strong additional energy near 700 Hz
```

without claiming what generated the 700 Hz component.

This should occur after basic event segmentation has been validated.

---

# 19. Baseline vs Event Comparison

A major V0.3 capability should be quantitative comparison between event and baseline intervals.

Examples:

```text
RMS ratio
band-power ratio
centroid shift
spectral-flatness difference
dominant-line changes
```

Example evidence:

```text
baseline RMS: 0.12
event RMS:    0.43
ratio:        3.58

baseline 500–1000 Hz power: 0.014
event 500–1000 Hz power:    0.182
ratio:                       13.0
```

This is stronger evidence than simply saying:

```text
an anomaly occurred.
```

---

# 20. Multiple Events

V0.3 must support zero, one, or many events.

Output should therefore contain:

```text
events: []
```

when no event is detected.

It must never create a placeholder or fabricated event merely because event detection was requested.

---

# 21. Event Summary

An analysis may provide an event summary such as:

```text
number_of_events
total_event_duration_s
fraction_of_record_in_events
maximum_deviation_score
strongest_event_id
```

This summary must derive entirely from detected event records.

---

---

# 23. Visualization

V0.3 should eventually generate an event-detection visualization containing:

```text
waveform
detected event regions

and/or

feature track
baseline
detection thresholds
detected event regions
```

Plots are engineering aids.

They are not validation evidence by themselves.

The numerical output remains authoritative.

---

# 24. Determinism and Reproducibility

For identical:

```text
input signal
sampling rate
configuration
software version
```

V0.3 must produce identical numerical event results.

Random methods are unnecessary for the initial V0.3 detector.

If random methods are introduced later, random seeds must be recorded.

---

# 25. Scientific Interpretation Boundary

Allowed:

```text
Three high-energy events were detected.

The strongest event occurred between 4.20 and 4.75 seconds.

Its short-time RMS reached 7.4 robust-scale units above baseline.

During this event, power in the 500–1000 Hz band increased by 12.8×.
```

Not allowed:

```text
A bearing fault occurred.

An electrical transient caused the event.

The event came from the cooling pump.

This anomaly proves equipment degradation.
```

Such conclusions belong to later investigation layers and require independent evidence.

---

# 26. Relationship With Future AI Layer

The future AI/agent layer may ask:

```text
Are there any unusual time periods?

Measure RMS around event 4.

Compare the event PSD with the baseline PSD.

Check whether the 700 Hz line appears only during the event.

Investigate other validated measurements.
```

The AI layer receives structured evidence.

It never invents:

```text
event times
RMS values
spectral powers
frequencies
deviation scores
```

Those values come only from validated DSP tools.

---

# 27. Explicitly Out of Scope

V0.3 does not include:

- multichannel anomaly detection
- cross-channel coincidence analysis
- correlation between sensors
- coherence
- source localization
- causal inference
- automatic fault diagnosis
- physical source attribution
- machine learning
- deep learning
- autoencoders
- Isolation Forest
- local LLM integration
- Ollama
- agentic investigation
- MCP tool exposure
- automatic noise suppression
- adaptive filtering
- real-time streaming detection

These remain later roadmap items.

# V0.3 Validation Matrix

# V3-01 Stationary Gaussian Noise

Signal:

```text
stationary white Gaussian noise
fixed seed
constant standard deviation
```

Purpose:

Verify that a stationary baseline does not generate spurious event activity.

Expected:

```text
stable short-time RMS distribution
finite baseline location
finite non-zero baseline scale
no persistent event
```

Acceptance:

For the fixed acceptance signal and reference detector configuration:

```text
detected events = 0
```

This is a reproducibility test, not a universal false-alarm guarantee.

---

# V3-02 Single High-Energy Burst

Signal:

```text
Gaussian background
+
one increased-amplitude interval
```

Example:

```text
event start = 4.0 s
event end   = 5.0 s
```

Purpose:

Basic event detection.

Expected:

```text
one event
event overlaps known injected interval
elevated short-time RMS
positive deviation score
```

Timing acceptance:

Detected boundaries must agree with the injected event within the temporal resolution imposed by the analysis window.

Initial tolerance:

```text
≤ one frame length
```

---

# V3-03 Increasing Event Amplitude

Use identical background realization.

Inject the same event using:

```text
A1 < A2 < A3
```

Expected:

```text
peak feature value increases monotonically

peak deviation score increases monotonically
```

This is a central quantitative validation.

---

# V3-04 Increasing Background Noise

Keep event amplitude constant.

Use:

```text
σ1 < σ2 < σ3
```

Expected:

```text
baseline RMS increases

event contrast relative to baseline decreases
```

The deviation score should reflect reduced event prominence.

---

# V3-05 Two Well-Separated Events

Inject:

```text
event 1
large quiet gap
event 2
```

Expected:

```text
number of detected events = 2
```

Event intervals must remain distinct.

---

# V3-06 Event Gap Merging

Inject two event intervals separated by:

```text
gap < configured merge gap
```

Expected:

```text
one merged event
```

Repeat with:

```text
gap > configured merge gap
```

Expected:

```text
two events
```

This validates segmentation rather than DSP measurement.

---

# V3-07 Minimum Duration Rejection

Inject an above-threshold disturbance shorter than:

```text
minimum_event_duration
```

Expected:

```text
event rejected
```

Inject a disturbance longer than the minimum duration.

Expected:

```text
event retained
```

---

# V3-08 Threshold Hysteresis

Construct a feature trajectory that fluctuates around the threshold.

Purpose:

Ensure small fluctuations do not create many fragmented events.

Expected:

```text
start only after start threshold is crossed

event remains active until end threshold condition is met
```

The expected segmentation can be calculated directly from the synthetic feature sequence.

---

# V3-09 Positive Impulse

Signal:

```text
stationary noise
+
large positive impulse
```

Purpose:

Validate short-time peak feature.

Expected:

```text
peak feature reacts strongly
```

Depending on frame length, RMS response may be smaller than the peak response.

---

# V3-10 Negative Impulse

Same as V3-09 but with a negative impulse.

Expected:

```text
absolute peak detector gives equivalent magnitude response
```

This ensures polarity does not incorrectly suppress impulse detection.

---

# V3-11 Constant Signal

Signal:

```text
x[n] = constant
```

Expected:

```text
short-time RMS constant
MAD = 0
baseline status = degenerate
no divide-by-zero
no NaN
no fabricated anomaly score
no fabricated events
```

---

# V3-12 Very Low-Level Signal

Use a finite signal with extremely small amplitude.

Purpose:

Numerical stability.

Expected:

```text
finite feature measurements
safe baseline handling
no overflow
no invalid logarithmic calculations
```

---

# V3-13 Reference-Interval Baseline

Signal:

```text
0–4 s       quiet reference
4–8 s       elevated activity
```

Configure:

```text
baseline interval = 0–4 s
```

Expected:

```text
baseline statistics calculated only from 0–4 s
event detected in elevated interval
```

Change the baseline interval deliberately.

Expected baseline statistics must change accordingly.

---

# V3-14 Sustained Step Change

Signal:

```text
normal level
↓
sudden increase
↓
remains elevated
```

Expected:

```text
one sustained event
```

This distinguishes event detection from impulse detection.

---

# V3-15 Return to Baseline

Signal:

```text
normal
elevated
normal
```

Expected:

```text
event begins after elevation
event ends after return
```

This validates both onset and termination.

---

# V3-16 Frequency-Band Event

Signal:

```text
stationary broadband background

during event:
add 800 Hz component
```

Measure:

```text
500–1000 Hz short-time band power
```

Expected:

```text
clear band-power increase during event
detected event overlaps injected interval
```

---

# V3-17 Out-of-Band Disturbance

Use the same detector band:

```text
500–1000 Hz
```

Inject a strong disturbance near:

```text
3000 Hz
```

Expected:

```text
500–1000 Hz band-power detector should not show a comparable event
```

This validates frequency selectivity.

---

# V3-18 Same RMS, Different Spectral Content

Construct two intervals having approximately equal total RMS but different spectral distributions.

Example:

```text
baseline:
broadband noise

event:
tone-dominated signal adjusted to similar RMS
```

Expected:

```text
total RMS detector may show little change

frequency-selective or spectral feature should reveal the change
```

This is an important V0.3 engineering test.

It demonstrates why "anomaly" cannot be defined only as increased amplitude.

---

# V3-19 Event Spectral Characterization

Inject an event containing:

```text
700 Hz
1400 Hz
2100 Hz
```

Background contains no such tones.

Expected during event:

```text
additional narrowband components
possible harmonic family near 700 Hz
```

Expected outside event:

```text
components absent or substantially weaker
```

The existing validated V0.2 harmonic and line measurements should perform the characterization.

The event detector itself must not duplicate those algorithms.

---

# V3-20 Event vs Baseline Power Ratio

Create controlled baseline and event intervals with a known amplitude scaling.

For amplitude scaling:

```text
event amplitude = 2 × baseline amplitude
```

For otherwise identical content, expected power relationship is approximately:

```text
event power ≈ 4 × baseline power
```

Purpose:

Validate event/baseline quantitative comparisons.

---

# V3-21 Event Ordering and IDs

Inject three events at known times.

Expected:

```text
event_001 < event_002 < event_003
```

Events must be returned in chronological order.

IDs must be deterministic.

```text

same baseline
same scores
same event intervals
```


# V3-27 Real-World Validation

After all synthetic acceptance tests pass, use at least two real measurement types.

Recommended:

```text
environmental audio with intermittent events

sensor or vibration data containing transient activity
```

Purpose:

Determine whether the validated detector behaves sensibly on non-synthetic data.

Real-world validation shall not establish source truth unless independently labelled ground truth exists.

The report should explicitly distinguish:

```text
measured
observed
inferred
unknown
```

# Core V0.3 Rule

The analyzer may report:

```text
An event was detected from 6.42 s to 7.11 s.

Short-time RMS increased from a baseline of 0.18
to a maximum of 0.67.

The maximum robust deviation score was 8.4.

Power between 500 and 1000 Hz increased by 11.2×.

A narrow spectral component near 720 Hz was present
during the event.
```

It must not report:

```text
The anomaly was caused by an electrical fault.

The 720 Hz component came from a motor.

The detected event proves equipment degradation.
```

The first group consists of measurements.

The second group consists of hypotheses or physical conclusions.

That boundary must remain intact when AI and agent layers are introduced later.
