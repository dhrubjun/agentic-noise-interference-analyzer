# V0.3 Engineering Specification

## Agentic Noise & Interference Analyzer

**Version:** V0.3  
**Name:** Event & Anomaly Detection  
**Status:** Complete  
**Depends on:** V0.1 Core Single-Channel Signal Analyzer and V0.2 Noise & Interference Characterization

---

# 1. Objective

V0.3 extends the validated single-channel analyzer from whole-record signal characterization toward detection of time-localized changes.

The objective is:

> Given one validated sampled signal, detect time intervals whose measured signal properties deviate significantly from an estimated baseline and describe those intervals using reproducible numerical evidence.

V0.3 remains a deterministic DSP system.

It does not use:

- LLMs;
- Ollama;
- machine learning;
- neural networks;
- agentic reasoning;
- automatic source identification;
- causal inference.

The processing philosophy is:

```text
Signal
  ↓
Validated V0.1/V0.2 DSP
  ↓
Short-time feature measurement
  ↓
Robust baseline estimation
  ↓
Deviation scoring
  ↓
Event segmentation
  ↓
Event measurements
  ↓
Optional spectral comparison
  ↓
Structured evidence
```

The analyzer detects measurable deviations.

It does not diagnose their physical cause.

---

# 2. Meaning of Event and Anomaly

## 2.1 Event

An event is:

> A contiguous time interval where a selected measured feature satisfies a defined event-detection rule.

Implemented V0.3 examples include:

```text
short-time RMS increased

selected-band power increased
```

An event is therefore a measurement result.

It is not automatically a fault, failure, or identified interference source.

---

## 2.2 Anomaly

For V0.3, anomaly means:

> A sufficiently large deviation of a measured feature from its estimated baseline according to the configured robust deviation and event-detection rules.

This does not mean:

```text
system failure
equipment fault
dangerous condition
known interference source
physical cause identified
```

Those interpretations require additional evidence.

V0.3 may report:

```text
A time-localized RMS event was detected.

The event peak was more than six robust-scale units
above the estimated baseline.
```

It must not report:

```text
A machine fault occurred.

The event came from a motor.

The disturbance was caused by the electrical mains.
```

---

# 3. Supported Input

V0.3 retains the existing signal assumptions:

- single-channel input;
- real-valued samples;
- uniformly sampled data;
- known sampling frequency;
- offline processing;
- finite validated samples.

V0.3 operates on the original signal together with validated V0.1 and V0.2 DSP measurements where appropriate.

Multichannel event relationships are deferred to V0.4.

# 4. Core Architecture

V0.3 separates the event-analysis problem into independent stages:

```text
Feature measurement
        ↓
Baseline estimation
        ↓
Deviation scoring
        ↓
Event segmentation
        ↓
Post-processing
        ↓
Event measurements
```

These stages are deliberately not hidden inside one opaque anomaly detector.

This allows every stage to be validated independently.

For example:

```text
Signal
  ↓
Short-time RMS
  ↓
Median/MAD baseline
  ↓
Robust deviation score
  ↓
Hysteresis
  ↓
Minimum-duration filtering
  ↓
Gap merging
  ↓
Event interval
```

The final result retains the numerical evidence produced by these stages.

---

# 5. Short-Time Framing

Event detection requires measurements that vary with time.

V0.3 divides a signal into frames using:

```text
frame_length_samples
hop_length_samples
```

Derived metadata includes:

```text
frame_length_seconds
hop_length_seconds
```

Only complete frames are analyzed.

Incomplete final frames are not automatically zero-padded.

Each frame is assigned a centre timestamp.

The framing configuration is retained as analysis metadata.

---

# 6. Short-Time RMS

The primary time-varying V0.3 feature is short-time RMS.

For each frame:

```text
RMS = sqrt(mean(x²))
```

Short-time RMS is useful for detecting:

- bursts;
- sustained amplitude increases;
- temporary increases in signal energy;
- intermittent high-energy disturbances.

The result is a time-varying feature track containing:

```text
times_seconds
rms
frame_length_samples
hop_length_samples
frame_length_seconds
hop_length_seconds
```

---

# 7. Short-Time Band Power

V0.3 also supports frequency-selective event analysis using short-time band power.

For each frame:

```text
frame
  ↓
Welch PSD
  ↓
selected frequency band
  ↓
integrated band power
```

Example:

```text
80–120 Hz
```

A temporary component near 100 Hz can therefore produce a strong band-power event even when other spectral regions remain unchanged.

This provides an important distinction between:

```text
overall signal-level changes
```

and:

```text
frequency-selective disturbances
```

The implementation reuses the validated V0.2 Welch PSD and band-power functions rather than implementing separate spectral calculations.

---

# 8. Generic Feature-Track Architecture

The baseline, deviation-score, hysteresis, and post-processing stages operate on numerical feature tracks rather than directly on raw RMS calculations.

This allows the same event-detection architecture to operate on:

```text
short-time RMS
short-time band power
```

and potentially on additional validated features in future versions.

New feature types must be independently validated before being used for event detection.

Short-time peak amplitude, spectral-centroid tracks, spectral-flatness tracks, and similar features are not part of the completed V0.3 release.

---

# 9. Robust Baseline Estimation

V0.3 uses a robust full-track baseline.

For feature values:

```text
x[0], x[1], ..., x[N-1]
```

the baseline location is:

```text
median(x)
```

The Median Absolute Deviation is:

```text
MAD = median(|x - median(x)|)
```

A Gaussian-equivalent robust scale is then calculated as:

```text
robust_scale = 1.4826 × MAD
```

The baseline result stores:

```text
location
mad
robust_scale
method
status
number_of_values
```

The implemented method is recorded as:

```text
median_mad
```

This robust estimator reduces the influence of isolated large feature values.

---

# 10. Baseline Limitations

The V0.3 baseline is estimated from the complete feature track.

This is appropriate when anomalous periods occupy a relatively small portion of the recording.

It is not universally valid.

For example:

```text
50% normal state
50% elevated state
```

may not be represented well by one global median/MAD baseline.

User-defined reference intervals, adaptive baseline tracking, and state-dependent baselines are deferred to later versions.

V0.3 therefore does not claim that its global baseline is suitable for every measurement scenario.

---

# 11. Degenerate Baseline Handling

A special case occurs when:

```text
MAD = 0
```

Then:

```text
robust_scale = 0
```

The baseline is marked:

```text
degenerate
```

The implementation does not silently replace zero with an arbitrary small denominator.

Standardized deviation scores are only calculated when the robust scale is valid and non-zero.

This avoids fabricated or numerically misleading anomaly scores.

---

# 12. Robust Deviation Score

For a valid baseline:

```text
score =
(feature_value - baseline_location)
/
baseline_robust_scale
```

For the implemented MAD baseline:

```text
score =
(feature_value - median)
/
(1.4826 × MAD)
```

This is a robust standardized deviation score.

For the current energy-related feature tracks, V0.3 uses positive deviations to identify unusually high feature values.

The score is not a probability.

For example:

```text
score = 6
```

does not mean:

```text
99.999% probability of failure
```

unless a separate statistical probability model has been established.

---

# 13. Hysteresis Event Detection

V0.3 uses separate thresholds for starting and ending an event.

Configuration:

```text
start_threshold
end_threshold
```

with:

```text
start_threshold > end_threshold
```

An event starts when:

```text
score >= start_threshold
```

Once active, it continues until:

```text
score < end_threshold
```

Example:

```text
start threshold = 6
end threshold   = 3
```

Hysteresis reduces fragmentation when the feature score fluctuates around the detection threshold.

---

# 14. Event Interval Information

Each raw event stores:

```text
start_index
end_index
start_time_s
end_time_s
duration_s
peak_index
peak_time_s
peak_score
```

The event timestamps correspond to the short-time feature samples.

The timing resolution is limited by the selected frame and hop lengths.

The analyzer must not imply timing precision beyond this analysis resolution.

---

# 15. Minimum Event Duration

V0.3 supports:

```text
minimum_event_duration_s
```

Events whose complete frame support is shorter than this value can be rejected.

The duration check uses full frame support rather than simply subtracting two frame-centre timestamps.

This is important because a one-frame event still represents a non-zero physical time interval.

---

# 16. Event Gap Merging

V0.3 supports:

```text
merge_gap_s
```

Two nearby event intervals may be combined when the time between their represented frame supports is sufficiently small.

This prevents one physical disturbance from being unnecessarily split because the deviation score briefly drops below the event-ending threshold.

Gap merging is a segmentation rule.

It does not imply that the merged intervals have the same physical cause.

---

# 17. RMS Event Measurements

For final RMS events, V0.3 calculates structured measurements including:

```text
start_time_s
end_time_s
support_duration_s
peak_score
peak_rms
mean_rms
baseline_rms
rms_ratio_to_baseline
```

For example:

```text
baseline RMS = 0.5
peak RMS     = 2.0

peak RMS / baseline = 4.0
```

These values describe the measured event.

They do not identify its physical source.

---

# 18. Frequency-Selective Event Detection

Short-time band-power feature tracks can use the same event-detection stages:

```text
short-time band power
        ↓
median/MAD baseline
        ↓
robust deviation score
        ↓
hysteresis
        ↓
minimum-duration filtering
        ↓
gap merging
        ↓
frequency-selective event
```

Synthetic validation demonstrated that an in-band tone produces a strong event while an out-of-band tone produces far less power in the selected detection band.

This validates the frequency-selective nature of the measurement.

---

# 19. Event vs Baseline Spectral Comparison

V0.3 provides deterministic spectral comparison between a baseline signal segment and an event signal segment.

The comparison reuses validated V0.2 spectral tools.

Implemented quantities include:

```text
baseline_total_power
event_total_power
total_power_ratio

baseline_band_power
event_band_power
band_power_ratio

baseline_centroid_hz
event_centroid_hz
centroid_shift_hz

baseline_spread_hz
event_spread_hz
spread_change_hz

baseline_flatness
event_flatness
flatness_change
```

The comparison allows evidence such as:

```text
Power in the 80–120 Hz band increased strongly.

The spectral centroid shifted downward.

The event spectrum became less spectrally flat.
```

It does not identify the source of the change.

Automatic event-level narrowband-line comparison and harmonic-family comparison are not integrated into the V0.3 event pipeline.

---

# 20. Zero, One, or Multiple Events

V0.3 supports:

```text
zero events
one event
multiple events
```

When no event is detected, the result contains an empty event collection.

The analyzer must not generate a placeholder or fabricated event merely because event analysis was requested.

---

# 21. Pipeline Integration

V0.3 is integrated into the existing single-channel analysis pipeline.

Configuration is optional through:

```text
event_analysis_config
```

If:

```text
event_analysis_config = None
```

V0.1 and V0.2 analysis behaves as before.

If V0.3 analysis is enabled:

```text
Signal
  ↓
V0.1 analysis
  ↓
V0.2 characterization
  ↓
V0.3 event analysis
```

If the input is constant, or a mathematically valid event baseline cannot be formed, event analysis safely returns unavailable rather than fabricating scores.

Backward compatibility with earlier pipeline behavior is tested.

# 28. Real-World Validation

V0.3 was evaluated on two real-world signal types after synthetic validation passed.

The purpose was not to establish physical ground truth.

The purpose was to verify that the validated event detector behaves sensibly when applied to real measurements.

---

## 28.1 Real Vibration Measurement

Dataset:

```text
samples:       30720
sample rate:   1024 Hz
duration:      30 s
Nyquist:       512 Hz
```

V0.3 configuration:

```text
frame length:              1024 samples
hop length:                256 samples
start threshold:           6
end threshold:             3
minimum event duration:    0.5 s
merge gap:                 0.25 s
```

Measured baseline:

```text
baseline RMS:    0.0018135461
MAD:             0.00022705652
robust scale:    0.000336634
status:          valid
```

Result:

```text
raw events:      0
final events:    0
```

The recording nevertheless contained substantial spectral structure.

V0.2 found multiple strong narrowband components and characterized the complete recording as tonal-dominant.

This is an important result:

> Persistent spectral structure does not automatically create a time-localized RMS event.

The V0.2 and V0.3 results therefore describe different signal properties rather than contradicting one another.

---

## 28.2 Real Environmental Audio

Dataset:

```text
samples:       220500
sample rate:   44100 Hz
duration:      5 s
Nyquist:       22050 Hz
```

V0.2 showed that approximately 94.94% of the measured power was below 250 Hz.

V0.3 configuration:

```text
frame length:              4410 samples
hop length:                2205 samples
start threshold:           6
end threshold:             3
minimum event duration:    0.2 s
merge gap:                 0.1 s
```

Measured baseline:

```text
baseline RMS:    0.20760039
MAD:             0.037511634
robust scale:    0.055614749
status:          valid
```

Result:

```text
raw events:      0
final events:    0
```

The recording contained strong low-frequency spectral energy but did not contain an RMS deviation large enough to cross the configured V0.3 thresholds.

Again:

> Persistent spectral characteristics were correctly separated from time-localized amplitude anomalies.

Thresholds were not lowered merely to force a detection.

---

# 29. Real-World Interpretation Boundary

The real-world experiments demonstrate that:

```text
no detected event
```

does not mean:

```text
nothing exists in the signal
```

It means only:

> No event satisfying the configured feature, baseline, deviation, and segmentation rules was detected.

For example, the vibration recording contained strong spectral lines but no qualifying short-time RMS event.

This distinction is essential for engineering interpretation.

# 35. Core V0.3 Rule

The analyzer may report:

```text
An event was detected during this time interval.

Short-time RMS increased substantially relative to
the estimated robust baseline.

The maximum deviation score was 8.4.

Power in the selected frequency band increased during
the event.

The event spectral centroid differed from the baseline.
```

The analyzer must not report:

```text
The anomaly was caused by an electrical fault.

The component came from a motor.

The disturbance proves equipment degradation.

This signal proves that one physical system caused another.
```

The first group consists of measurements.

The second group consists of hypotheses or physical conclusions.

That boundary must remain intact when AI and agent layers are introduced later.
