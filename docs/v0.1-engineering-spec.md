# V0.1 Engineering Specification

## Agentic Noise & Interference Analyzer

**Version:** V0.1  
**Status:** Approved baseline  
**Purpose:** Core single-channel signal analyzer

---

## 1. Objective

V0.1 establishes the validated DSP foundation of the Agentic Noise & Interference Analyzer.

The objective is:

> Given a single sampled signal and its sampling information, produce validated time-domain, frequency-domain, and time-frequency-domain measurements together with reproducible numerical results and plots.

V0.1 is deliberately a **classical DSP system**.

It does not contain an LLM, AI agent, machine-learning model, or automatic physical source interpretation.

The fundamental processing philosophy is:

```text
Input Data
    ↓
Validated DSP Calculation
    ↓
Numerical Measurement
    ↓
Visualization
```

The numerical DSP engine is intended to remain authoritative even when an AI layer is introduced in later versions.

---

## 2. Scope

V0.1 supports:

- one signal at a time;
- real-valued samples;
- uniformly sampled signals;
- CSV input;
- known sampling frequency or a valid time column;
- offline analysis.

The initial analyzer will calculate:

- basic signal information;
- time-domain statistics;
- waveform;
- FFT and amplitude spectrum;
- Power Spectral Density (PSD);
- Amplitude Spectral Density (ASD);
- spectrogram;
- spectral peaks.

Analysis parameters and numerical results must be preserved for reproducibility.

---

## 3. Input Data

### 3.1 Sample-Only CSV

Example:

```text
signal
0.124
0.482
-0.137
...
```

The sampling frequency must be supplied separately.

Example future CLI usage:

```text
python analyze.py measurement.csv --fs 10000
```

---

### 3.2 Time and Signal CSV

Example:

```text
time,signal
0.0000,0.124
0.0001,0.482
0.0002,-0.137
...
```

The analyzer may infer the sampling frequency from the time spacing if the timestamps are sufficiently uniform.

The inferred sampling frequency must be reported.

The analyzer must not silently treat nonuniform data as uniformly sampled.

---

## 4. Signal Representation

Internally, a signal should be represented using a structured data model such as `SignalRecord`.

Conceptually:

```text
SignalRecord
├── samples
├── sample_rate_hz
├── number_of_samples
├── duration_seconds
├── nyquist_frequency_hz
├── channel_name
├── units
├── source_file
└── metadata
```

Unknown metadata must remain explicitly unknown.

The analyzer must not assume that an uploaded signal represents:

- voltage;
- acceleration;
- acoustic pressure;
- seismic displacement;
- SDR IQ data;
- or any other physical quantity.

For example, if units are unknown, plots should use:

```text
Amplitude [arbitrary units]
```

rather than inventing physical units.

---

## 5. Input Validation

Validation must occur before numerical DSP analysis.

The analyzer should check:

- input file exists;
- CSV can be parsed;
- selected signal column exists;
- samples are numeric;
- signal is not empty;
- sampling frequency is numeric, finite, and positive;
- sufficient samples exist for the requested analysis;
- samples do not contain NaN;
- samples do not contain positive or negative infinity;
- whether the signal is constant;
- whether timestamps are approximately uniformly spaced.

NaN and Inf values should initially cause explicit validation failure rather than being silently repaired.

Nonuniformly sampled signals must not be silently resampled.

Possible clipping may be indicated only when justified by available information. The analyzer must not claim ADC clipping when ADC limits are unknown.

---

## 6. Basic Signal Information

For each signal, the analyzer should determine and report:

- number of samples;
- sampling frequency;
- sampling interval;
- signal duration;
- Nyquist frequency;
- data type;
- minimum sample value;
- maximum sample value.

For a sampling frequency \(F_s\):

$$
T_s = \frac{1}{F_s}
$$

and:

$$
f_{\mathrm{Nyquist}} = \frac{F_s}{2}
$$

---

## 7. Time-Domain Statistics

V0.1 will calculate:

- mean;
- median;
- RMS;
- standard deviation;
- variance;
- minimum;
- maximum;
- peak-to-peak amplitude.

For samples \(x[n]\), RMS is:

$$
x_{\mathrm{RMS}} = \sqrt{\frac{1}{N}\sum_{n=0}^{N-1}x[n]^2}
$$

Peak-to-peak amplitude is:

$$
x_{\mathrm{pp}} = x_{\max} - x_{\min}
$$

These calculations must be validated against analytically known signals.

---

## 8. Waveform

The analyzer will generate a time-domain waveform.

If the sampling frequency is known:

```text
x-axis: Time [s]
```

If physical signal units are known, they should be used on the y-axis.

Otherwise:

```text
y-axis: Amplitude [arbitrary units]
```

Visualization is downstream of the numerical DSP engine and must not be treated as the authoritative numerical result.

---

## 9. FFT and Amplitude Spectrum

For real-valued signals, V0.1 will initially provide a one-sided spectrum from:

```text
0 Hz → Fs/2
```

The frequency resolution for a record containing \(N\) samples is:

$$
\Delta f = \frac{F_s}{N}
$$

FFT analysis must preserve or report:

- sample count;
- sampling frequency;
- frequency resolution;
- window;
- normalization method.

Amplitude normalization must be handled correctly for one-sided spectra.

Windowing must be explicit rather than hidden.

The project should distinguish between:

- raw FFT;
- windowed FFT;
- amplitude spectrum;
- PSD.

These quantities must not be treated as interchangeable.

---

## 10. Windowing

Windowing will be investigated and validated using controlled signals.

In particular, a non-bin-centered sinusoid will be used to demonstrate spectral leakage.

The initial experiments should compare at least:

- no window;
- Hann window.

The analyzer must record which window was applied.

Window selection should never be hidden from the analysis record.

---

## 11. Power Spectral Density

V0.1 will calculate Power Spectral Density using Welch's method.

Important parameters include:

- sampling frequency;
- window;
- segment length (`nperseg`);
- overlap (`noverlap`);
- FFT length if explicitly selected;
- scaling.

A Hann window is the initial expected default.

The exact default segment length should be selected and validated during implementation rather than being arbitrarily frozen in advance.

If input units are volts, PSD units are:

```text
V²/Hz
```

If physical units are unknown:

```text
amplitude²/Hz
```

Where practical, integrated PSD power should be checked against the corresponding time-domain signal power.

---

## 12. Amplitude Spectral Density

Amplitude Spectral Density is defined as:

$$
ASD(f) = \sqrt{PSD(f)}
$$

If the signal is measured in volts, ASD units are:

```text
V/√Hz
```

Otherwise:

```text
amplitude/√Hz
```

A fundamental numerical validation is:

$$
ASD(f)^2 = PSD(f)
$$

within floating-point tolerance.

ASD is a first-class output because it is particularly useful for noise-analysis applications.

---

## 13. Spectrogram

The spectrogram provides time-frequency information for signals whose spectral content changes with time.

The analysis must preserve:

- window;
- segment length;
- overlap;
- frequency resolution;
- time resolution.

The fundamental tradeoff must remain visible:

```text
Longer segment
    → better frequency resolution
    → poorer time resolution

Shorter segment
    → poorer frequency resolution
    → better time resolution
```

The spectrogram implementation will be validated using an intermittent interference signal whose start and stop times are known.

---

## 14. Spectral Peak Detection

V0.1 will identify significant spectral peaks.

Peak detection should eventually support controlled criteria such as:

- minimum prominence;
- minimum spacing;
- optional minimum height.

The implementation should not simply return the numerically largest FFT bins because adjacent bins from the same spectral component could otherwise be incorrectly reported as separate signals.

Peak frequency and associated spectral magnitude should be returned as structured numerical results.

---

## 15. Outputs

A future analysis run may produce:

```text
outputs/
└── run_001/
    ├── results.json
    ├── analysis_config.json
    ├── waveform.png
    ├── spectrum.png
    ├── psd.png
    ├── asd.png
    └── spectrogram.png
```

The exact run-directory implementation will be developed later in V0.1.

Numerical results must not exist only inside plots.

---

## 16. Reproducibility

Each analysis should preserve enough information to reproduce the result.

This includes, where applicable:

- input filename;
- selected signal column;
- sampling frequency;
- number of samples;
- duration;
- units;
- analysis methods;
- DSP parameters;
- software version;
- analysis timestamp.

Example PSD configuration:

```json
{
  "psd": {
    "method": "welch",
    "window": "hann",
    "nperseg": 4096,
    "noverlap": 2048
  }
}
```

The configuration used to produce a result is part of the scientific result.

---

## 17. Software Architecture

The DSP implementation must remain independent of the user interface.

Initial architecture:

```text
CLI
 │
 ▼
Analysis Pipeline
 │
 ▼
DSP Engine
```

DSP calculations must not be embedded directly inside CLI code.

This allows the same validated DSP engine to later support:

```text
                     DSP ENGINE
                         ▲
           ┌─────────────┼─────────────┐
           │             │             │
          CLI          Web GUI        Agent
                                      │
                                    Ollama
```

The future agent must call the same validated DSP functions rather than implementing numerical signal processing through the LLM.

---

## 18. Explicitly Out of Scope

V0.1 does not include:

- Ollama;
- LLM integration;
- investigation agent;
- agentic tool selection;
- MCP;
- machine learning;
- multichannel analysis;
- cross-correlation between measurement channels;
- cross-spectral density;
- coherence;
- automatic source attribution;
- causal inference;
- noise-source classification;
- noise cancellation;
- adaptive filtering;
- real-time processing;
- SDR hardware interfaces;
- streaming;
- cloud deployment;
- full web application.

These features belong to later development stages.

## 20. V0.1 Completion Criterion

V0.1 is complete when the analyzer can:

> Analyze one real-valued uniformly sampled signal from CSV; validate the data; calculate basic statistics, FFT/amplitude spectrum, Welch PSD, ASD, spectrogram, and spectral peaks; generate plots; save structured results and important parameters; and pass the approved synthetic validation suite before being trusted on real-world datasets.

The primary objective of V0.1 is not feature quantity.

It is to establish a **trustworthy, validated, and reusable DSP foundation** for all later versions of the Agentic Noise & Interference Analyzer.
